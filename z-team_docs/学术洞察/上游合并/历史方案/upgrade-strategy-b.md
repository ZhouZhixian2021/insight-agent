# 上游升级解耦方案（v3）

> 历史原稿：数量、路径、命令和实施状态保留当时背景。当前使用请从 [上游合并资料](../00-目录.md) 进入，勿用历史工具覆盖仓库现行实现。

> v2 的四处执行缺陷已在 v3 修正：合并方向、生成物的局部性与顺序、门禁的实际有效性、验收命令与仓库要求对齐。
> 配套：`upgrade-kit/`（门禁脚本 + 登记表，尚未进仓库）。

## 0. 与 v2 的差异

| # | v2 的问题 | v3 的修正 |
|---|---|---|
| 1 | 从 `upstream/master` 开分支再合 `master`，`--theirs` 指向我们自己的分支 | 从 `master` 开 `upgrade/<ver>`，合**固定的上游 SHA**；`ours`=我们、`theirs`=上游 |
| 2 | 所有生成物整文件取上游；`xargs` 不适合 PowerShell | 生成物分三类（全量生成 / 局部生成 / 派生），顺序锁定为"源码 → 依赖清单 → lockfile → 生成器 → 幂等校验"；改用 `--restore-generated` 与 PowerShell 原生步骤 |
| 3 | 校验脚本恒成功，预算 175 仍可 +18 | 默认失败：`owner/reason` 必填、`fork` 数量封顶在**当前 129**、分类与文件实际标记比对、`--against` 拦截新增 fork 路径 |
| 4 | 验收没按 `build:artifacts → build:check`；`rerere.autoupdate` 直接开 | 验收门改为仓库要求的顺序；`rerere` 开、`autoupdate` 关，逐次人工确认复用结果 |

## 1. 分叉现状（重新分类）

`upstream/master` = `687f282e86`；差异 1173 = 998 新增 + 175 修改 + 0 删除。

| 类别 | 数量 | 说明 |
|---|---|---|
| 生成物（全量或派生） | **40** | 含 25 个 `.i18n.yaml` 双语一致性记录、15 个 catalog/图/快照类文档、4 个生成代码、lockfile |
| 接线（patch/preset） | 6 | |
| 源码改写 | **129** | 真正需要人工决策的部分 |

v2 把生成物算成 12 个，是因为只认英文 `Generated by` 标记；中文版文档的标记写作"由 … 生成——请勿手工编辑"，`.i18n.yaml` 则是 `verify-translation-pairing --write` 的产物，两者都漏掉了。

129 个源码改写按规模：`1–3 行` 45、`4–10 行` 52、`11–50 行` 28、`51–200 行` 3、`>200 行` 1。

## 2. 合并方向（修正 1）

```sh
UPSTREAM_SHA=$(git rev-parse upstream/master)     # 固定本次升级引入的上游提交
git switch master
git pull --ff-only origin master
git switch -c upgrade/<ver>
git merge --no-ff "$UPSTREAM_SHA"
```

Git 的 `ours` / `theirs` 指**合并中两条线的身份**，不是"谁的版本更新"：

| 场景 | `ours` | `theirs` |
|---|---|---|
| 从 `master` 开分支，合上游 SHA（v3） | 我们 | **上游** |
| 从 `upstream/master` 开分支，合 `master`（v2，错） | 上游 | 我们 |

评审面也顺带变清楚了：

```sh
git log --oneline master..upgrade/<ver>     # 本次引入的上游提交，一条不多
git diff master..upgrade/<ver>              # 上游带了什么 + 我们解冲突时改了什么
```

## 3. 生成物处置（修正 2）

生成物不是"整文件取上游"就完事，按来源分三类：

| 子类 | 判定 | 例子 | 处置 |
|---|---|---|---|
| **G1 全量生成** | 文件整体由脚本产出 | `docs/config-catalog.*`、`docs/module-graph.*`、`api-catalog.ts`、`known-event-types.ts`、`slot-catalog.ts` | 取上游 → 跑生成器 → 期望与该生成器输出一致（`git diff --exit-code`） |
| **G2 局部生成** | 文件含生成区 + 手写区 | 部分 subsystem 文档、带 `<!-- generated -->` 区块的页面 | 取上游 → 跑生成器 → 只允许手写区产生差异；手写内容要迁到独立文件或生成输入里 |
| **G3 派生** | 由其他已定稿内容算出 | `pnpm-lock.yaml`、`*.i18n.yaml` | **最后**重算；lockfile 由 `pnpm install` 从定稿的依赖清单算出，翻译记录由 `verify-translation-pairing --write` 重算 |

关键顺序（v2 把顺序弄反了）：

1. 先解**源码**冲突（`packages/**`、`apps/**`）；
2. 再解**依赖清单**冲突（`package.json`、`pnpm-workspace.yaml`、`tsconfig*.json`）；
3. 依赖清单定稿后才跑 `pnpm install`——lockfile 冲突时不要手工合并，先接受任一侧，再让 pnpm 重算；
4. 跑生成器（`gen-*`）；
5. 重算翻译记录（`verify-translation-pairing --write`）；
6. **幂等校验**：`git add -A` 后再跑一遍 3–5，`git status --porcelain` 必须为空。

PowerShell 步骤（替代 `xargs`）：

```powershell
node scripts/upgrade/verify-upstream-overrides.mjs --restore-generated   # 内部执行 git checkout --theirs
pnpm install
pnpm run gen-cordis-api; pnpm run gen-config-catalog; pnpm run gen-doc-graphs
pnpm run gen-module-graph; pnpm run gen-persistence-catalog; pnpm run gen-cordis-catalog
git add -A
# 第二遍：确认生成器幂等
pnpm run gen-cordis-api; pnpm run gen-config-catalog; pnpm run gen-doc-graphs
pnpm run gen-module-graph; pnpm run gen-persistence-catalog; pnpm run gen-cordis-catalog
if (git status --porcelain) { throw '生成器非幂等：第二遍产生了新差异' }
```

`--restore-generated` 由脚本自己逐个执行 `git checkout --theirs -- <path>`（不用管道，跨 shell 可用）。

## 4. 门禁（修正 3）

脚本 `scripts/upgrade/verify-upstream-overrides.mjs` + `upstream-overrides.json`，**与代码一起进版本管理**。

判定矩阵（全部默认失败）：

| 检查 | 条件 | 结果 |
|---|---|---|
| 未登记修改 | 改了上游文件但不在登记表 | FAIL |
| 登记过期 | 登记了但实际没差异 | FAIL（升级窗口内可用 `--allow-stale`） |
| 字段缺失 | `owner` / `reason` 为空 | FAIL |
| 分类不符 | 标记为 `generated` 但文件无生成标记，或反之 | FAIL |
| fork 增长 | fork 文件数 > `budget.maxForkFiles`（= 当前 129） | FAIL |
| 新增 fork 路径 | `--against <ref>` 下出现基线里没有的 fork 路径 | FAIL |

实测（本仓库）：

```
$ node verify-upstream-overrides.mjs            # 未填字段
fork 129/129  modified 175  added 998  registered 175
  FAIL missing-owner: .agents/notes/.../2026-06-24-web-capability-seam.i18n.yaml
exit=1

$ node verify-upstream-overrides.mjs            # 填满后
overrides: in budget                            exit=0

$ # 预算收到 120
FAIL fork-budget-exceeded: 129 fork files > budget 120            exit=1
$ # 删掉一条登记
FAIL unregistered-modification: packages/plan/plan-mode/src/index.ts   exit=1
$ # 把生成物错标为 fork
FAIL category-mismatch: docs/config-catalog.md (carries a generated marker ...)   exit=1
```

接入：

```json
"upgrade:check": "node scripts/upgrade/verify-upstream-overrides.mjs",
"upgrade:report": "node scripts/upgrade/verify-upstream-overrides.mjs --report"
```

CI 里用 `--against origin/master`，`owner/reason` 与新路径都要在 PR 中被显式批准（登记表加 CODEOWNERS）。

## 5. 验收门（修正 4，对齐 AGENTS.md）

`AGENTS.md` 要求 `build:check` 跑在最新的 `build:artifacts` 之后（或直接 `pnpm run build`）。顺序：

| # | 命令 | 说明 |
|---|---|---|
| 1 | `pnpm run build:artifacts` | 先产出，后续检查依赖它 |
| 2 | `pnpm run typecheck` | 上游接口变化最快暴露 |
| 3 | `pnpm run lint` | |
| 4 | `pnpm run build:check` | 必须紧跟在步骤 1 的产物之后 |
| 5 | `pnpm exec vitest run <受影响包>` | 聚焦行为测试 |
| 6 | `pnpm run test:snapshot`、`pnpm run test:expected` | 可见输出 |
| 7 | `pnpm run doc-sync` | 文档联动，最后 |
| 8 | 推送后等 CI | 本地绿 ≠ CI 绿 |

`rerere`：开启，但 `rerere.autoupdate` **关**。每次自动复用解法后 `git diff` 确认，确认无误再 `git add`；连续几次升级都稳定后才考虑开 autoupdate。

## 6. 台账与预算

记录：日期 / 上游版本 / 上游 SHA / 冲突文件数 / 冲突 hunk 数 / 本次新增 fork 数 / 门禁结果。

红线：
- 冲突文件数连续两次上升 → 暂停加功能，做一轮降级；
- 同一 fork 文件连续三次升级被上游改动 → 上游化或插件化；
- fork 数超过登记预算 → 门禁失败（预算只降不升）；
- 生成物第二遍重算产生差异 → 失败。

## 7. 降级路线

**P1：40 个生成物归零（半天）** —— 全部转为"重算"，人工不参与。重点是确认我们的生成输入不在上游文件里（若在，迁成我们自己的新文件）。

**P2：97 个 `1–10 行` 改动（2–3 天）** —— 逐条判断：文档表格行 → 生成器输入；tsconfig references → `gen-tsconfig-paths` 或自有 tsconfig；导出行 → `*.patch.yml` 或自有 barrel。

**P3：4 个 `>50 行` 改动** —— 上游化 / 插件化 / 永久登记（附测试）。

目标：fork 129 → ≤40。

## 8. 落地顺序

1. 把 `scripts/upgrade/`（脚本 + 登记表）纳入版本管理，接 CI（非 strict 不可用，直接生效）；
2. 补齐 129 条 fork 的 `owner/reason`（`--report` 出清单），这是门禁转绿的前置条件；
3. P1 → P2 → P3；
4. 用一次真实升级验证：冲突文件数应显著低于历史。
