# 二次开发对照清单与维护要求

[返回上游合并资料](00-目录.md)

本说明把已有升级方案中的登记要求和当前脚本字段汇总为团队入口，不重新生成一份与代码脱离的清单。依据为 [当前检查脚本](../../../scripts/upgrade/verify-upstream-overrides.mjs)、[原 v3 方案](历史方案/upgrade-strategy-b.md) 与 [T0 功能清单](验收基线/t0-feature-checklist.md)。

## 两份对照各解决什么问题

| 对照对象 | 维护位置 | 要回答的问题 |
| --- | --- | --- |
| 改写上游文件 | [upstream-overrides.json](../../../scripts/upgrade/upstream-overrides.json) | 改了哪里、谁负责、为什么需要改、升级时如何处理 |
| 业务功能与验收 | [T0 功能基线](验收基线/t0-feature-checklist.md)，后续增量写入 [开发记录](../开发记录/00-目录.md) | 计划审批、检索、去重、证据、报告、取消与恢复等功能是否保留，有什么验证依据 |

文件登记表只覆盖上游已有文件的改写，不能当成全部二次开发功能清单。独立新增模块也可能受上游接口变化影响，仍需做业务对照和回归检查。

## 文件级清单怎么填

| 字段 | 通俗含义 | 维护要求 |
| --- | --- | --- |
| `path` | 改动文件的位置 | 使用相对仓库根目录的路径，文件移动后同步调整 |
| `category` | 这是什么改动 | `fork`：人工改写；`generated`：可重建生成物；`wiring`：接入配置或连接点 |
| `owner` | 谁负责解释和处理 | 填实际维护人，不能只把自动推断的最近提交者当作已确认负责人 |
| `reason` | 为什么要改这个文件 | 说明业务需要及为什么不能只新增独立模块；不能只写“适配升级” |
| `addedLines` / `removedLines` | 差异规模 | 属于统计信息，重新对比后更新，不代表个人工作量 |
| `upstreamChurn6mo` | 上游近期改动频率 | 用于辅助判断维护风险，不是冲突发生的确定结论 |

表头的 `upstream.baseline`、`upstream.recordedAt` 说明登记背景；`budget.maxForkFiles` 是人工改写数量预算；`generatedExemptions` 是生成物标记检查的例外。生成物还应与 [重建映射](../../../scripts/upgrade/generated-map.json) 对齐。

现行登记以链接的 JSON 文件和实际检查结果为准，不能把条目数量当作检查已通过。最近一次补登、维护责任归口与预算差额见 [2026-11-04 登记补齐结果](2026-11-04-登记补齐结果.md)；[2026-11-03 核对记录](2026-11-03-登记核对结果.md)保留原始历史证据。

## 每次开发与升级怎么维护

1. 开发时确认是否改到上游已有文件，必要时更新登记项及负责人、原因；新增业务功能在对应开发记录中写清验收入口。
2. 升级前固定团队代码和上游目标的提交，记录范围，并核对已登记改写与上游变化的重叠位置。
3. 合并时区分人工代码、接入配置和生成物；生成物按当前工具规则重建，不能机械套用历史方案中的命令或路径。
4. 升级后分别检查文件登记和业务行为。业务对照应写明：功能、原行为、升级后结果、验证材料、负责人、遗留问题；保留原有失败或能力限制的说明。
5. 在开发记录登记实际运行的检查、失败原因和提交状态。未运行、部分通过、已通过分开写；不以构建成功替代真实流程验证。

## 当前只读检查入口

在仓库根目录使用以下检查，执行结果可能暴露已提交代码中的未登记改动或已有问题。当前脚本以共同基线到 `HEAD` 的差异计算文件集合，不覆盖未提交的业务增量；未提交改动须另行核对。

```powershell
pnpm run upgrade:check
pnpm run upgrade:check:strict
node scripts/upgrade/verify-upstream-overrides.mjs --report
```

普通检查核对登记、分类、必填字段和预算；当前严格入口还与 `origin/master` 对照新增的人工改写路径。`--report` 用于查看缺少负责人或原因的条目。构建、生成物重放及完整业务验收按当前工具说明和对应模块计划另行执行，本次资料整理不执行升级合并或生成物重建。
