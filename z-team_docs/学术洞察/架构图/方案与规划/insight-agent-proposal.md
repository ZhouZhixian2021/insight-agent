# 洞察 Agent（Insight Agent）方案 —— 基于 DeepSeek Harness 构建

> 状态：草案
> 结论先行：**底座选型 dsh（已定），Preset 分组采用方案 D（3 preset + 4 skill）**

---

## 1. 背景与目标

当前技术洞察完全依赖人工：耗时长、覆盖面受限于个人精力、结论沉淀在个人脑中无法复用。LLM agent 技术已经成熟到可以让"扇出式调研 + 结构化分析 + 综合成文"这条流水线自动化。

四个场景共享同一个骨架：**定范围 → 证据扇出 → 结构化抽取 → 交叉分析 → 综合成文**，因此是**一套底座 + 分组 preset + 场景方法论（skill）**，而不是四个独立系统。所有场景写入同一个证据库，互相供血——产品分析引用学术演变结论、新闻简报检测与历史证据库重叠的趋势信号，这正是人工做时最耗时的部分。

## 2. 市场产品：现有产品没有覆盖这个组合

| 维度 | 通用 Deep Research | Elicit（学术） | DeepWiki（代码） | 本方案 |
| --- | --- | --- | --- | --- |
| 工作流骨架 | ✅ | 仅抽取 | 仅单仓库 | ✅ |
| 穷尽性 | 广而浅 | 表格级 | 单仓库 | 全量：会议所有论文、产品全部 changelog |
| 结构化中间产物 | 无（报告即终点） | 有 | 无 | ✅ 证据库为底座，报告只是视图 |
| 固定分析框架 | 模型自由发挥 | 无 | 无 | ✅ 方法论沉淀为 skill |
| 跨分析积累 | 无状态 | 弱 | 无 | ✅ 证据库持续复用、增量更新 |
| 持续跟踪 | 一次性 | 否 | 否 | ✅ 新闻场景定时输出、新 proceedings 增量更新 |

**结论**：流程骨架已被通用 Deep Research 验证成立；结构化抽取已被 Elicit 验证有价值；但"结构化证据库 + 领域方法论 + 跨分析积累 + 持续跟踪"的完整组合市面上是空白——因为它需要我们的个性化的人工洞察经验，恰是通用产品最难吞掉的差异化。

| 要点 | 含义 | 落点 |
| --- | --- | --- |
| 领域方法论 | 分析师"怎么看问题"（固定看哪些维度、按什么框架对比、依据什么下结论）写成 agent 照着走的清单 | 经验 → 沉淀为 skill |
| 跨分析积累 | 分析一次的成果永久入库，本次分析站在前次的肩膀上，而不是每次从零爬起 | 证据库共享 |
| 持续跟踪 | 从"做一次分析"变成"订阅这个领域"：系统定时自动运行，基于历史基线做增量 diff，告诉你"什么变了" | 证据库增量更新 |

方法论决定**深度**（单次分析的质量），积累决定**厚度**（分析间的复利），跟踪决定**鲜度**（时效）；三者共同的地基是结构化证据库——方法论作用于库、积累就是库本身、跟踪是库的增量更新。

## 3. 总体架构

### 3.1 模型层：按认知负荷分层（模型路由）

| 环节 | 负荷 | 模型策略 |
| --- | --- | --- |
| 抽取（单篇论文/单个页面 → 结构化记录） | 低，schema 受限 | 快速便宜模型 + schema 校验兜底 |
| 分析（聚类、时间线、对比矩阵） | 中 | 中档模型 + embedding 分类 |
| 综合写作、下判断、给观点 | 高 | 最强模型 |

### 3.2 智能体架构：编排者 + 子 agent + 证据库

三条设计原则：

1. **子 agent 的核心价值是上下文隔离**。50 篇论文 × 15 页绝不进主循环；每个子 agent 拿干净上下文深读一篇，返回固定 schema 的结构化记录。主 agent 只见骨架，不进血肉。
2. **中间产物是结构化证据库，不是文本流转**。所有抽取结果落持久化 store（论文表：主张/方法/指标/年份/主题向量；产品表：能力/版本轨迹/社区指标；新闻表：事件/来源/关联技术）。
3. **确定性流水线为主，自主性只留两处**。用 pipeline 编排 + agent 填充认知环节（抽取/归纳/写作），远比"一个大 agent 自由发挥"稳定。自主性只保留在范围规划和完整性自查。

主流程：

```
规划 agent：分析框架、证据清单、补搜计划
   ↓
扇出：每篇论文/每个维度/每天的信源一个子 agent，结构化抽取入库（2012文章）
   ↓
分析：聚类 → 时间线/对比矩阵/能力雷达（部分纯代码，不耗模型）
   ↓
批判 agent：覆盖完整性检查 + 论断-证据一致性
   ↓
写作 agent：分章节起草 → 修订循环 → 统稿
   ↓
人在环上：先审大纲再写正文（人工经验注入点，便宜的重定向）
```

### 3.3 结构化证据库（核心）

**定义**：把 agent 读过的所有材料，从"一堆文本"变成"可以查询、可以关联的表格"。agent 每读一篇论文/一个仓库页面/一条新闻，强制产出一条结构化记录落库；报告里的每个论断都必须链回库里的记录，库里的每条记录都链回原始材料。

**记录形态示例**（学术场景，每篇论文一条）：

```json
{
  "id": "paper-042",
  "title": "XXX: A Fast Consensus Protocol for Geo-Distributed Systems",
  "venue": "OSDI 2026",
  "year": 2026,
  "problem": "跨地域部署下共识延迟过高",
  "method": "基于仲裁迁移的分片共识",
  "metrics": [{ "name": "p99 延迟", "value": "12ms", "baseline": "Raft 47ms" }],
  "claims": [
    { "text": "跨三地域 p99 延迟降至 Raft 的 1/4", "evidence_ref": "paper-042#sec6.2" }
  ],
  "theme_vector": [0.12, -0.87],
  "relates_to": ["paper-017", "paper-033"]
}
```

| 优点 | 机制 |
| --- | --- |
| **可审计（防幻觉）** | 写作 agent 只允许引用证据库条目；报告论断点击可跳回原始证据（`evidence_ref`）；无对应记录的论断在批判环节被拦下。幻觉从"不可检测"变成"可机器检查" |
| **可计算（分析质变）** | 技术演变分析从"LLM 读完 80 篇凭感觉归纳"变成数据库操作：聚类用 `theme_vector`、时间线按 `year`、对比矩阵用 join——分析环节一半是纯代码，不耗模型，又便宜又可靠 |
| **可积累（跨分析复用）** | 会议分析入库后学术演变直接查表；新闻简报与历史证据 join 做"这条新闻是不是三个月前那篇论文的产业化信号"——人工洞察最贵的关联工作变成一个 join |

**物理形态**：关系型数据库（结构化字段与论断）+ 向量索引（embedding，聚类与相似检索），做成 dsh-insight 插件组的一个 capability，以 `evidence_store` / `evidence_query` 工具暴露给 agent。结构化证据 先以"抽取结果落 JSON 文件"的最简形态验证 schema，P2 固化为 DB。

**落盘的三个层次**（只有中间层是必须的核心）：

| 层次 | 内容 | 落盘策略 |
| --- | --- | --- |
| 原始材料 | PDF、网页、changelog 原文 | 可选缓存，仅为省重复爬取；丢了可重抓 |
| **结构化抽取记录** | 上述 JSON 记录本体 | **必须落盘，证据库本体**。每篇论文读一次、抽一次、永久入库；即使原文不缓存，`evidence_ref` 链接也在 |
| 分析结论 | 报告、对比矩阵、趋势判断 | 存档，但定位为"视图"——原则上任何报告都能从第二层重新生成 |

**可行性分析**：

| 维度 | 依据 | 结论 |
| --- | --- | --- |
| 技术组件 | 关系型 DB（SQLite/PG）+ 向量索引（sqlite-vec/pgvector）均为成熟基础设施，零新发明 | 无技术风险 |
| LLM 结构化抽取 | schema 约束输出（structured output + JSON 校验重试）是已验证模式；Elicit 已证明论文级结构化抽取可规模化 | 模式已被市场验证 |
| schema 设计依据 | 字段来自我们人工洞察实际使用的分析维度（分析师比较什么） | 人工经验 |
| 抽取质量 | schema 校验拦截格式错误；批判 agent 抽检内容错误；抽取任务本身认知负荷低，便宜模型 + 校验即可达标 | 风险可控 |
| schema 演进 | 结构化落库用文件形态低成本磨 schema，DB才固化 | 有现成工程先例 |

### 3.4 系统架构：三层

- **证据采集层**：`web_search` / `web_fetch` / `paper_search` / `schedule`（均以 dsh capability 形式挂载）+ 爬虫（GitHub API、arXiv/DBLP、会议官网）。工程量最容易被低估，决定上限。
- **知识层**：结构化 DB + 向量库 + 累积的洞察记忆。跨分析复用是长期价值。
- **产出层**：报告为入口、证据库为产物；新闻场景输出定时推送。

### 4.1 候选对比

| | 自研框架 | Claude Agent SDK\通用Deep research | **dsh** |
| --- | --- | --- | --- |
| agent 循环/工具调用/重试 | 全部自己写 | 现成 | 现成 |
| 子 agent / 扇出 | 自己实现 | 现成 | 现成（subagent capability） |
| pipeline 编排 | 自己实现 | 需自建编排层 | 现成（workflow capability） |
| 长任务持久化恢复 | 自己实现 | 有 | 现成（durable session，核心设计） |
| 多场景配置切换 | 自己实现 | 代码级 | **preset 机制原生支持** |
| 定时任务 | 自己实现 | 需自建 | headless profile + ACP + `schedule` 工具 |
| 模型分层策略 | 自己实现 | 支持 | 支持（llm provider 是可替换 seam） |
| 领域方法论沉淀 | 自己设计 | skill 支持 | **skill capability** |
| 代码所有权 | 无上游依赖 | 依赖 Anthropic | **我们自己的项目，可按需改引擎** |

### 4.2 选定理由

1. **能力映射一一对应**：四个场景需要的每块积木 dsh 都有现成 capability，选型即组装。
2. **preset/skill 机制天生匹配产品形态**："一套底座 + 分组 preset + 场景方法论"恰好就是 dsh 的 per-session agent composition from preset cordis.yml，不需要任何架构适配。
3. **代码所有权是决定性优势**：长时任务恢复、跨 session 知识沉淀遇到引擎层缺口时直接改 harness，不用给上游提 issue 等排期。

## 5. Preset 分组方案(静态动态都对比一下)

### 5.1 四个业务的工具需求（暂定）

| 业务 | 需要的工具 | 特点 |
| --- | --- | --- |
| 学术洞察 | `paper_search` + `web_search` + `web_fetch` + `analysis_generate` | 独占 paper_search，其他通用 |
| 产品洞察 | `web_search` + `web_fetch` + `analysis_generate` | 纯通用工具 |
| 会议洞察 | `web_search` + `web_fetch` + `analysis_generate` | 纯通用工具，**和产品完全一样** |
| 新闻洞察 | `web_search` + `web_fetch` + `schedule` + `analysis_generate` | 独占 schedule（定时） |

关键观察：**产品和会议的工具集一模一样**，差异仅在方法论（skill）和人设上。

### 5.2 四个候选方案

**方案 A：纯 Skills（4 个 skill 塞进一个静态 agent）**
全部 5 个工具全局挂载，4 个 skill、1 个人设。
问题：模型同一时间看到 5 个工具（总有 2 个当前业务用不到）→ token 浪费 + 误选风险；4 个业务挤一份会话历史，互相污染；一个 persona 无法兼顾四个身份；没有升级到分组形态的天然路径，基本等于重做。

**方案 B：一个 Preset + 4 个 Skills**
统一人设 + 全部工具挂载 + 4 个 skill。
和 A 的根本问题一样——工具全开的噪声随业务数线性增长，学术看到 schedule、新闻看到 paper_search。唯一改进是 skill 之间互不干扰。

**方案 C：一业务一 Preset（完全隔离）**
4 个 preset，各自独立人设 + 最小工具集。
隔离最彻底，但产品和会议工具集完全一样：同一个 `web_search` 在两个 preset 里各注册一次，维护两份几乎相同的 `agent.cordis.yml`，改一个必须同步改另一个——多出来的那个 preset 没有带来额外价值。

**方案 D：分组 Preset（推荐，后续可能工具集变动，再分）**
按"工具集 + 人设可否共用"分组：

```
preset: "academic-insight"
├── persona: 学术研究分析师
├── 工具：paper_search + web_search + web_fetch + analysis_generate
└── skill: academic/

preset: "competitive-insight"     ← 产品 + 会议合并
├── persona: 技术竞争力分析师（兼顾产品与会会议，靠 skill 切换方法论）
├── 工具：web_search + web_fetch + analysis_generate
└── skills: product/ + conference/

preset: "news-insight"
├── persona: 前沿科技新闻分析师
├── 工具：web_search + web_fetch + schedule + analysis_generate
└── skill: news/
```

分组依据：工具集一样

### 5.3 横向对比

preset **决定“这个会话由哪些插件、怎么组合而成”**。一份 cordis.yml，声明这个 agent 由哪些插件拼起来、各插件怎么配置。

| 升级路径 | 🔴 基本重做 | 🟢 可平滑拆分 | 🟢 已是最优态 | 🟢 已是最优态 |

## 0. Executive Summary

**做什么**：将人工技术洞察自动化为一个 agent 系统，覆盖四个场景——学术（论文演变分析）、产品（技术竞争力分析）、会议（全景扫描）、新闻（每日/每周前沿简报）。四场景共享一套底座和一个结构化证据库，互相供血。

**为什么值得做**：市面上通用 Deep Research 验证了流程可行，但"结构化证据库 + 领域分析框架 + 跨分析积累 + 持续定时跟踪"这个完整组合是空白——它需要我们的领域方法论，是通用产品吞不掉的差异化（方法论决定深度、积累决定厚度、跟踪决定鲜度，三者都不在模型里）。人工周级的分析压缩到小时级，且洞察从一次性文档变成可复用、可审计的资产。

**怎么做**：一条流水线——规划 → 子 agent 扇出抽取 → 结构化入库 → 交叉分析 → 批判校验 → 写作，人在环上只审大纲和终审。模型按认知负荷分三层（抽取用便宜模型、写作用最强模型）。技术核心是**结构化证据库**：所有论断链回库内记录、库内记录链回原始材料。

**为什么用 dsh**：所需积木（agent 循环、subagent、workflow、durable session、preset、skill、定时）dsh 全部现成，选型即组装；preset/skill 机制与产品形态一一对应；引擎层缺口可以直接改。

**产品形态（方案 D）**：3 个 preset + 4 个 skill。产品和会议工具集完全一样、人设可共用，合并为竞品组靠 skill 切分方法论；学术独占 `paper_search`、新闻独占 `schedule`，各自独立 preset。后续拆分/合并只看两个信号：长出独占工具、或人设不能共用。
