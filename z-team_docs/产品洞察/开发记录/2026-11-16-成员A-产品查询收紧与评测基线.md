# 产品查询收紧与评测基线

成员 A，分支 dev/zhouzhixian2021-new。本地开发，未提交或推送。

## 问题

首轮搜索直接把产品名、问题全文和计划范围拼成一条查询，实测平均 179.5 字符、最长 211 字符。搜索引擎会截断长查询，并用范围散文里的通用词匹配，返回大量与产品无关的页面；计划范围本身是“关注方向”的描述，进入查询后反而把检索收窄到猜测的措辞上。此前的验收只看个别会话是否出了报告，没有可重复的量化口径。

## 修改

`source/src/index.ts` 新增 `productSearchQuery()`：查询由产品名称和问题里最显著的至多 4 个关键词组成，关键词按 ASCII、含数字、长度打分后排序，总长不超过 60 字符并按空格边界截断。产品名末尾的括号注释视为说明而不是检索词；名称已包含的词不再重复。计划范围不再进入查询。缺口补搜保持原逻辑，仍带产品名、关键词与获批的版本地区。

同时建立本地评测工具 `.dsh-runtime/bench/`：`bench-product.mjs` 从会话日志还原每轮的有效页率、证据/调用、查询字数、失败分类、未答问题与交付状态，`compare-product.mjs` 输出改动前后的对照表和判定。两份基线分别保存为 `results/a-before-query-shorten.json`（7 轮）和 `results/b-after-query-shorten.json`（3 轮）。

## 验证

- `productSearchQuery` 三个单元用例：长度上限与范围剔除、ASCII 关键词优先、括号注释和重复词去除。
- `pnpm exec vitest run packages/product-insight`：108 项通过；`pnpm run typecheck` 通过。
- 评测对照：基线 7 轮中位数有效页率 64%、证据/调用 4.0、平均查询 179.5 字符；改造后 3 轮为 75% / 43% / 35%，中位数 43%、证据/调用 3.19、平均查询 23.8 字符、未答 0/4、三轮均为 final。
- 与同条件对照会话 `session-d29aba30`（准入未收紧、长查询，有效页率 17%、证据 35 条、1.46 条/次）相比，证据量提升约九成。

## 限制

- 预先登记的成功标准是有效页率 ≥85%、证据/调用 ≥6.0，3 轮结果未达到，因此没有把这次改动记为“问题已修复”，只记为有效改善。
- 同一份代码单轮波动在 17%~100% 之间，3 轮不足以定论，结论需要更多轮次的中位数支撑。
- 垃圾页面仍然存在（游戏开发论坛、旅游站、赌场站等），当时无法判断来自哪个搜索引擎，留作下一步。
- 评测脚本保存在本地 `.dsh-runtime/`，没有入库，换机器需要重新准备。
