# 搜索来源稳定化方案

成员 A，2026-11-18。讨论稿；P1 已实施，P2 进行中。

## 背景

产品洞察的候选网页来自三个 HTML 搜索引擎（DuckDuckGo、Bing、Yahoo），由 `source/src/multi-search.ts` 直接抓取结果页并解析 DOM。这套做法在 2026-11-18 的一轮实跑里同时失效：

| 引擎 | 本轮状态 |
|---|---|
| duckduckgo | `WEB_PROVIDER_CHALLENGE`（要求验证码） |
| yahoo | `unsupported content type "unknown"` |
| bing | 返回无关结果：查询「苹果 M6 芯片」得到「恭喜祝福语」「MYR 兑换 USD」「新加坡物业登录页」 |

结果：计划阶段的搜索把 7 个无关网址带进候选池，占 30 个名额的 23%，全部 0 证据；该轮证据从 123 条掉到 69 条。

失败根源不是解析器写错，而是**把三个搜索引擎的 HTML 当成唯一入口**，且默认它们会正常返回。任何一个引擎改版或反爬，都会直接冲击发现阶段。

## 目标与约束

| 约束 | 含义 |
|---|---|
| 不引入 API key | 不使用 Brave、Exa、Tavily、Perplexity 等需要注册或付费的接口 |
| 尽量稳定 | 来源改版不应导致整条链路失效，最坏情况可自动降级 |
| 无需频繁更新 | 维护频次按季度而不是按周计 |
| 发布不繁琐 | 不新增服务、不新增第三方依赖、不改打包流程 |
| 覆盖不退步 | 长尾评测站仍要能拿到 |

自建 SearXNG 因需要运维而被排除；带 key 的官方 API 因约束一被排除。

## 实测证据

2026-11-18 对候选方案做了四次探测：

| 探测地址 | 结果 |
|---|---|
| `bing.com/search?q=apple+m6+chip&format=rss` | 200，标准 RSS 2.0，**但内容与 HTML 版一样无关**（翻译网站、词典） |
| `bing.com/news/search?q=apple+m6&format=rss` | 200，**高度相关**：MacBook Pro M6 评测、卫报评测、iMac M6 评测、Forbes、Geeky Gadgets，条目带 `pubDate` 与来源名 |
| `apple.com/newsroom/rss-feed.rss` | 200，标准 Atom：标题、链接、更新时间、分类、摘要齐全 |
| `bing.com/news/search?...&mkt=zh-CN` | 退化，只返回一个壁纸推广链接 |

两个结论：

1. **Bing 网页搜索在当前网络环境下本身就退化**，RSS 与 HTML 返回同样的无关内容，说明问题不在我们的解析器；
2. **RSS/Atom 是公布的标准契约**，解析面远小于 DOM，改版概率极低。

## 方案

三层来源加一层与来源无关的防护。

```
L0 官方结构化源   官网 RSS/Atom、sitemap.xml       权威，几乎不改版
L1 结构化聚合源   Bing News RSS、Wikipedia、GitHub  keyless，标准契约
L2 HTML 兜底      现有 DuckDuckGo / Bing / Yahoo    保留但降级为补充
──────────────────────────────────────────────────
防护层            相关性校验、广告位过滤、源冷却
```

### L0 官方结构化源

从计划的 `officialUrl` 出发，按顺序尝试：

1. 页面内 `<link rel="alternate" type="application/rss+xml">` 自动发现；
2. 常见路径探测：`/newsroom/rss-feed.rss`、`/feed`、`/rss.xml`、`/blog/feed`；
3. `sitemap.xml` 或 `sitemap_index.xml`：只取网址列表，不抓正文。

`officialUrl` 由计划生成、随产品变化，所以这条规则对任何产品都成立，不含厂商硬编码。

### L1 结构化聚合源

| 来源 | 协议 | 覆盖内容 | 备注 |
|---|---|---|---|
| Bing News RSS（英文 mkt） | RSS 2.0 | 评测、新闻 | 实测相关度高；有使用条款限制 |
| Wikipedia REST API | JSON | 产品背景、规格沿革 | 公开 API，稳定 |
| GitHub Releases API | JSON | 软件类产品的版本与变更 | keyless 限额 60 次/小时 |
| npm registry / PyPI | JSON | 软件版本 | 稳定 |
| Hacker News（Algolia） | JSON | 技术社区讨论 | 稳定 |
| Google News RSS | RSS | 新闻 | 视网络可达性，可能不可用 |

中文覆盖目前只靠 L2 与官方中文站：`mkt=zh-CN` 实测退化，不纳入方案。

### L2 现有 HTML 引擎

选择逻辑不变，只增加两件事：

1. **广告位与推荐位过滤**：丢弃 `b_ad` 一类容器，即使同时带 `b_algo` 类名（做法参考 `dsh-search-tools`）；
2. **结果相关性校验**：查询词项与标题、摘要的匹配度，域名黑名单，站点根与导航页排除（导航页排除已在 2026-11-17 那版实现）。

### 防护层

- 每个来源输出统一结构并保留来源标签，沿用现有引擎归因（`discoveryChannel: web:<engine>`）；
- 来源连续失败 N 次后本轮跳过并记录，不阻塞其他来源（现有 `Promise.allSettled` 已保证隔离）；
- 部分来源成功即返回结果，全部失败才报错，并在日志里写清每个来源的状态。

## 为什么这样可以少维护

| 方案 | 需要 key | 改版风险 | 覆盖面 | 长期维护 |
|---|---|---|---|---|
| 纯 HTML 抓取（现状） | 否 | 高 | 中 | 每季度 |
| L0 官方 RSS / sitemap | 否 | 极低 | 低 | 接近零 |
| L1 结构化 API / RSS | 否 | 低 | 中 | 低 |
| SearXNG 自建 | 否 | 低 | 高 | 需要运维，已排除 |
| Brave / Exa / Tavily | 是 | 低 | 高 | 已排除 |

维护面从「三个搜索引擎的 DOM」缩到「RSS/Atom 与 JSON 契约」，且最坏情况只是某类来源失效，整体仍能出结果。

## 发布影响

- **零新增第三方依赖**：RSS/Atom 与 JSON 用 Node 内置能力加现有 `parse5` 即可，不引入 `impit`、`cheerio` 一类重型依赖，打包与发版流程不变；
- **配置化**：来源开关、超时、条数上限进入 `Config`，不写成代码常量；
- **离线契约测试**：每个来源保存一份真实响应样本作为固定数据，CI 不联网也能验证解析；线上是否失效由非阻塞的定时探测发现。

## 风险与限制

| 风险 | 说明 |
|---|---|
| Bing RSS 使用条款 | 明确限定在 RSS 聚合器内个人非商业用途，商业发布前需法务确认；备选是官方 RSS、Wikipedia、GitHub 这类明确允许的源 |
| 中文覆盖 | `mkt=zh-CN` 实测退化，中文只能靠 L2 与官方中文站 |
| 长尾评测站 | 结构化来源拿不到 notebookcheck、vpsspark 这类站点，仍需 L2 |
| 条数上限 | RSS 通常只给 10–50 条，不如搜索引擎灵活 |
| 官方站无 RSS | 部分产品官网不提供订阅源，L0 会退化为只读 sitemap |

## 分阶段任务

| 阶段 | 内容 | 预估 | 可验证收益 |
|---|---|---|---|
| P1 | L0 官方 RSS / sitemap 发现与解析 | 1 天 | 官方发布稿自动进入候选 |
| P2 | L1 Bing News RSS、相关性校验、广告位过滤 | 1 天 | 无关结果不再入池 |
| P3 | 来源健康度冷却与离线契约测试 | 0.5 天 | 单一来源失效时自动降级 |
| P4（可选） | Wikipedia、GitHub Releases | 1 天 | 软件类产品覆盖更好 |

## 验收标准

1. 用最近两轮的真实候选网址回放：无关结果占比降到 5% 以下；
2. 三个 HTML 引擎全部失效时，仍能拿到至少 10 个相关页面；
3. 连续 5 轮实跑，候选相关率不低于 80%；
4. 所有解析测试离线可跑，不依赖网络。

## 实施记录

### 2026-11-18 P1 第一步：发现与解析模块

新增 `source/src/official-feed.ts`（12 个离线测试，全部通过；source 包 69 个测试通过）。模块只做发现与解析，暂未接入发现流程。

真实站点验证：`https://www.apple.com/mac/` 与 `https://www.apple.com/newsroom/` 都能发现官方 Newsroom 订阅源，取回最新 5 条官方发布，带标题、发布时间、链接。

实现中遇到三个 HTML 解析与 XML 不一致的问题，已在模块内处理并加测试：

| 问题 | 后果 | 处理 |
|---|---|---|
| `<link>` 是 HTML 空元素 | RSS 的链接文本被丢弃 | 解析前把 `<link>文本</link>` 改名为 `rsslink` |
| CDATA 段被当作注释 | Atom 的标题、时间全部丢失 | 解析前把 CDATA 内容转义为普通文本 |
| 自闭合的未知元素不闭合 | `<category/>` 之后的兄弟节点被吞掉，条目链接读不到 | 解析前把 `<x .../>` 补成显式结束标签 |

遗留问题，交给 P2 的相关性过滤：

- 官方订阅源是站点级的，苹果的 Newsroom 订阅源会同时返回 F1、播客这类与产品无关的条目；
- 站点地图兜底返回的是站点导航页（首页、可访问性页等），排序按字母而非时间。

### 2026-11-18 P1 第二步：接入发现流程

发现阶段在计划链接之后、搜索之前读取官方订阅源，官方条目与搜索结果共用同一候选池和上限：

| 位置 | 改动 |
|---|---|
| `source/src/index.ts` | `ProductDiscoveryAdapters` 增加可选 `officialFeed`；新增 `discoveryChannel: 'official-feed'` 记录 |
| `workflow/src/index.ts` | `ProductInvestigationAdapters` 增加可选 `officialFeed`，转发给发现阶段 |
| `workflow/src/session-tool.ts` | 用 `web.fetch` 实现官方源读取，预算 8 次请求、最多 6 条链接 |

两类过滤避免官方站点的无关内容占位：

- **产品线词元**：从产品名与别名中提取带数字的词元（如 `m6`、`iphone18`），标题或路径命中才入池，避免厂商名（如 `apple`）把全部公司新闻都匹配进来；
- **导航页排除**：沿用既有规则，站点根、登录页等不进入候选。

订阅源失败记为一条发现阶段失败，不中断搜索；这一点有测试覆盖。

已知限制：官方源探测是串行且有请求次数上限（8 次），但**没有单次请求的时间上限**，站点响应慢时会拖长发现阶段。超时预算留到 P3 与来源冷却一起处理。

### 2026-11-18 首轮实跑与修正

第一轮实跑（session-81eb6d25）：30 个候选、读了 16 个页面、142 条证据、报告 75,348 字符、结算 final，但**没有一个 `official-feed` 候选**。

真正的原因不是订阅源窗口不够，而是**顺序错了**：模块先按条数截断（取最新 6 条），再交给发现阶段做产品线过滤；苹果订阅源里 10 月的两条 M6 发布稿排在更后面，被提前截断丢弃。

修正：把"是不是本产品"的判断下发给模块，在截断之前过滤；某个来源一条都不命中时继续尝试下一个来源（订阅源 → 站点地图）。

修正后对同一站点重放：

```
订阅源 https://www.apple.com/newsroom/rss-feed.rss：20 条，命中 2 条
MATCH Apple introduces the new 14-inch MacBook Pro with M6
MATCH Apple unveils new iMac with M6
```

教训：**先过滤再截断**。任何"取前 N 条再筛选"的管线，都会在热门站点上丢掉目标内容。

### 2026-11-18 P2 第一步：结果相关性判定

新增 `source/src/relevance.ts`（11 个离线测试；source 包 83 个测试通过），只做判定，尚未接线。

准入信号按强弱排序，命中一条即通过：

| 信号 | 权重 | 依据 |
|---|---|---|
| 产品线词元（`m6`、`iphone18`） | 最高 | 词元本身就把「这个产品」和「这家公司的其他新闻」分开 |
| 产品名或其词 | 次之 | 名称命中通常意味着页面在讲这个产品 |
| 规范问题词项 ≥ 2 个 | 最低 | 标题没写型号、但摘要覆盖了问题里的多个概念 |

三条实现细节：

- **ASCII 按词边界匹配**：否则 `m6` 会命中 `M600`、`printer driver` 这类无关页；
- **单字词元忽略**：中文分词器把「核心数」拆成「核心」「数」，把「带宽」拆成「带」「宽」，单字会把任意页面凑成 2 个命中；
- **只判元数据**：标题、摘要、路径，不读正文，因此可在抓取之前决定是否入池。

未接线的原因：一旦用它替换现有的 `screenCandidate`，focus 计划里没有命中任何信号的搜索结果不再入池，会改变候选数量，`discovery.spec.ts` 与 `workflow` 两条测试链的夹具需要同步重写。接线与广告位过滤、Bing News RSS 一起做，避免同一批夹具改两遍。

下一步（P2 剩余）：接线到 `screenSource`、`multi-search.ts` 的 `b_ad` 广告位过滤、Bing News RSS 来源。

### 2026-11-18 P2 第二步：接线与广告位过滤

相关性判定接进发现流程，搜索结果按来源区分处理：

| 来源 | 是否做元数据检查 | 理由 |
|---|---|---|
| 官网页面、官方订阅源条目 | 否 | 前者是唯一固定域名，后者已按产品线词元过滤过 |
| 用户点名的站点 | 否 | 用户已确认它是本产品的信息来源 |
| 搜索结果的其它页面 | 是 | 引擎会把无关页排进结果，这正是本轮要挡住的一类 |

排除发生在抓取之前，`screening.reason` 直接写明缺了哪些信号（例如 `Metadata names neither the product nor 2 approved question terms (matched 0).`），不需要再重新推断。

广告位过滤按容器类名判断，而不是只看结果卡片上的类名：Bing 的推广位会保留 `b_algo` 标记，靠卡片类名无法区分。实现沿父链检查 `b_ad` / `b_adBlock` / `b_ads` / `b_ans` 四类容器，命中即丢弃。

测试改动：`discovery.spec.ts` 里「没有产品名匹配的页面也入选」这一条不再成立，改为断言它被排除且理由包含缺失信号；其余 28 条发现测试与 86 条工作流测试均未受影响。`multi-search.spec.ts` 新增广告位用例，同时覆盖「推广卡片自带 `b_algo`」与「卡片包在 `b_adBlock` 里」两种形态。

剩余（P2 最后一项）：Bing News RSS 来源。
