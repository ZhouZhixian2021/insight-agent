## 配置与调用追踪

### 自定义路由缺少推理能力声明

当前 Web 配置中的 `abc` 路由使用 `openai-completions` 协议，模型为 `volcengine/deepseek-v4.1-flash`。该模型条目只包含 `id`、`name`；提供方没有配置 `reasoning`、`thinkingBudgets` 或 `compat`，模型条目没有配置 `reasoningEfforts`。本记录不复制密钥、认证变量内容或接口地址。

[catalog.ts](../../packages/llm/llm-pi-ai/src/catalog.ts) 的 `resolveModelReasoning()` 在没有声明、也没有该路由的内置模型条目时，将本地推理能力描述为 `false`；[adapter.ts](../../packages/llm/llm-pi-ai/src/adapter.ts) 的 `reasoningInfo()` 因此不暴露推理强度选项。这个本地能力描述不代表上游服务器关闭了推理。实际抽取请求的持久配置中没有 `reasoningEffort`，响应却包含推理块。

本地实际安装的 pi-ai 为 1.1.0。其 OpenAI Completions 实现只有在模型声明推理能力且兼容格式匹配时，才会使用对应的启停映射；例如 `deepseek` 格式可发送 `thinking.type`。当前模型声明未满足这些条件。这里只核对了本地序列化路径，没有抓取认证 HTTP 请求，也没有通过上游 API 验证具体关闭参数。

### 抽取与聊天沿用同一推理策略

[Controller](../../packages/api/academic-research-controller/src/index.ts) 从 Session 请求头或 Agent 选项选择模型，仅在会话已提供时携带 `reasoningEffort`。证据抽取和最终合成分别设置输出预算，但没有分别配置推理策略。新加入的逐题覆盖评估也使用抽取模型配置。

[model-call.ts](../../packages/academic/workflow/src/model-call.ts) 通过 `prepareCall()` 解析模型能力，将实际配置持久化后派发。[LLM 服务](../../packages/llm/llm/src/index.ts) 对没有声明推理能力的模型拒绝显式推理强度。因此仅在当前 Controller 请求里强行加 `reasoningEffort: off`，可能在发送前就被拒绝，不能作为已验证修复。

### 分块和输出预算放大单次开销

全文由程序下载解析，范围审核读取选出的文字窗口，随后证据抽取按片段分别调用模型；不是先让模型完整通读全文，再分块重复通读。当前片段约束默认最多 4,000 字符，每篇最多 8 次抽取派发，包含重试，单篇内按顺序执行。每次调用都可能产生一轮长推理。

当前每次抽取的输出预算为 16,384 token。这个值是上限，不表示模型必然生成这么多，但它允许本次观测到的数千至上万 token 输出。完整抽取取消了默认五条证据停止条件，使单篇可能派发更多片段；它增加调用数量，但不会自行启用推理。

## 后续修复顺序

1. 核对当前网关实际支持的推理启停字段，补齐对应模型的 `reasoningEfforts` 与兼容格式声明，确保程序能表达并发送真实的关闭或降低推理指令。
2. 为证据抽取提供单独、明确的推理策略，分别决定范围审核、逐题覆盖评估和最终合成的设置，避免用全局会话设置统一控制所有研究阶段。不可通过降低 `maxTokens` 冒充关闭推理，否则可能截断证据 JSON。
3. 参数协议确认后，用固定原文核对耗时、原文摘录与问题关联质量；用户此前要求自行测试，本轮没有执行此项验证，也不承诺关闭推理后的速度和质量。
4. 向量检索可后续用于减少送入模型的原文片段；当前日志尚不足以证明检索或本地核验是主要瓶颈，优先处理每次抽取的长推理开销。
