# 2026-09-29 检索渠道与报告进度接线

## 范围

本次解决实时进度复核发现的三个 A 侧遗漏：查询活动启动时没有携带已批准渠道；混合检索没有发布 Web 发现、引用识别和逐条引用核验事实；报告活动只显示 `rendering`，没有在质量评估的真实执行点显示 `evaluation`。已合并的全文候选和证据模型进度不重复修改。

## 已完成

- `DraftPipelineSearch` 将每条查询及其批准的 `academic`、`web_discovery` 渠道一起交给工作流；Controller 从已审核计划填入渠道，调用 Academic Source 时只传原有查询字段。
- 查询活动在搜索发起前发布批准渠道，因此 Web 发现失败时不会留下空渠道；渠道表示批准并实际发起的检索路径，不从终态结果或错误反推。
- 混合检索在真实 `searchWeb()` 调用前后发布 Web 发现事实，在同步引用识别前后发布候选数与已识别引用数，并为每一条 `verifyReference()` 发布从一开始的位置、总数、实际 Provider 和结算状态。
- 工作流把这些事实映射到现有检索活动；`operation` 区分学术源直接搜索、Web 发现、引用识别和引用核验，避免把 URL、引用与论文记录混成一个计数。订阅者异常不会影响检索结果。
- `generateReport()` 接受可选同步观察器，在质量检查前发布 `evaluation`，在 Markdown 组装前发布 `rendering`；观察器异常不会改变报告。
- 工作流使用报告包的真实操作通知更新报告活动。模型综合仍属于 `analysis` 阶段，不在报告阶段重复发布 `synthesis`。

## 边界

本次没有修改模型 Provider 的错误记录，也没有把 Web 编排职责移入 Academic Source。底层模型传输诊断继续属于 LLM Provider 的独立问题。

## 验证

对应测试覆盖 Web 失败前的批准渠道、三类混合检索操作的开始与结算、逐条核验位置、观察者异常隔离、报告操作顺序，以及 Controller 对旧纯学术计划和第 3 版混合计划的渠道投影。
