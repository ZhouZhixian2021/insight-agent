# Agent Note：词项排序后限制候选模型审核数量

状态：已实施

[English](2026-10-19-bounded-academic-candidate-review.md) | 中文

## 问题

一条已批准查询可能返回许多通过硬筛选的论文，而最终候选上限仅在排序后应用。若逐篇串行调用 Session 模型，候选筛选耗时就随发现记录增加。模型可能把多数输出 token 用于内部推理，在输出简短审核 JSON 前耗尽 150 秒的单次尝试期限；这段时间页面上的筛选阶段也不更新。

## 决策

Controller 在模型调用前生成确定性评估和排序，再通过[纯送审选择器](2026-10-20-academic-candidate-review-selection.zh.md)先分配问题覆盖名额、后按词项初排补齐。`candidateReviewMaximumWorks` 默认在初轮和证据缺口轮之间共用 8 篇额度，独立于 Plan 候选上限。`candidateReviewConcurrency` 默认 1，部署时可以显式选择 2。工作协程共享一个有序队列，在取消或致命存储失败后停止领取任务，并在返回前等待在途调用结束。已完成结果按选择顺序和规范论文身份归并，可恢复的模型失败保留其他成功结果及词项评估。

模型只接收批准主题、去重后的研究问题、范围规则及规范学术标题／摘要，返回范围和带引文的问题匹配。Controller 使用独立的版本化 Session 事件记录选择、准确请求、结算流和已验证判断，历史初筛事件继续可读。只有持久保存且校验通过的判断参与计分。实际派发后失败也消耗共享额度，派发前取消和准入拒绝不计入。`CandidateAssessment.semanticReview` 记录有效范围、未知、失败代码或未送审原因，Q6 与恢复检查点保留此状态；历史评估可缺少此字段。已有审核进度数量继续独立于去重论文总数。

## 考虑过的替代方案

**提高单次超时或输出 token 上限。** 这不能限制串行调用次数；模型若持续生成内部推理，整轮耗时反而可能增加。

**把词项低分作为硬排除。** 这会阻止模型挽救元数据稀疏或跨语言但确实相关的论文。符合硬规则的低分论文仍可由覆盖选择器或词项补足选中。

**把跳过的论文计为模型已审核。** 这会掩盖语义判断与词项回退的质量差异，因此评估和进度页面都明确区分二者。

## 结果

即使学术来源返回更多原始记录，整轮语义模型调用次数仍有上限。代价是限额之外的相关论文可能保留较低的词项分，未能进入最终候选上限。部署方可调整审核限额，但已批准的候选上限仍有约束力。单篇审核仍可能耗尽 `candidateReviewAttemptTimeoutMs`；这项决策不改变所选模型的内部推理行为，也不保证整轮有固定时长。

[固定评分交接包](../../../../z-team_docs/验收数据/2026-10-20-candidate-review/scoring-handoff/manifest.json)在实际评估和队列之外保留批准输入及已验证判断。无需密钥的重放调用正式纯函数，保留规范身份及每轮准确的查询来源。候选问题匹配与证据支持覆盖保持区分；重放一致不代表独立相关性评测通过。
