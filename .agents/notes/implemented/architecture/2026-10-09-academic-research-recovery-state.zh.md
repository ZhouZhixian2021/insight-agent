# Agent Note：学术研究恢复状态

状态：已实施

[English](2026-10-09-academic-research-recovery-state.md) | 中文

## 问题

学术研究已经把已批准检索计划、候选批次决定、批次结算及运行终态写入 Session 事件，但工作流没有公开的归一化回放边界。后续继续执行逻辑可能因此对已完成批次、待处理候选、覆盖状态或终态作出不同解释，并错误地重复工作。

## 决策

Academic workflow 通过仅含类型的 `@deepseek-ai/dsh-academic-workflow/recovery` 入口导出 `AcademicResearchRecoveryState` 契约。

成功重建时得到 `AcademicResearchRecoveryInput`。它把一个 RetrievalRun 和一个准确的 ResearchBrief 版本绑定到已批准检索计划、已完成批次事实、已调度但没有匹配结算的候选，以及最近一次已提交的逐题覆盖。已完成批次保留原候选顺序和结算计数；待处理候选保留批次编号和决定顺序；已批准查询身份和表达式直接复用，不重新生成。

外层状态区分 `resumable`、`completed`、`cancelled` 和 `failed`。已完成和已取消属于终态，不属于失败。重建失败时不携带继续执行输入，只返回稳定失败代码和经过净化的说明；失败文本不得包含原始模型响应或来源文档。

A-S2 新增纯折叠函数 `reconstructAcademicResearchRecoveryState()`，输入一份完整 Session 日志。调用方提供准确的 RetrievalRun 和 ResearchBrief 身份。折叠函数关联目标运行前最近的检索计划，配对每个已调度批次及其后续结算，保留最后一个未结算批次，恢复最近一次已提交覆盖，并识别终态结算。重复或不连续批次、重复候选、无调度的结算、累计证据数倒退、终态后的批次事实及 Brief 身份冲突都会被拒绝。新结算事件携带覆盖；缺少该字段的历史事件继续兼容，覆盖为空。

A-S3 在每个批次“已调度”和“已结算”边界写入带版本且可安全序列化为 JSON 的 `AcademicResearchRecoveryCheckpoint`。检查点保留继续执行所需的准确候选交接、论文／版本状态、排序策略、Q5 观察、累计论文结果、失败、覆盖和调度计数。`AcademicResearchRunRequest.resumeRetrievalRunId` 请求 Session 后端恢复目标运行；Controller 先通过 `resolveAgent()` 取得 Session 写入句柄，再重建状态。继续执行会跳过检索和筛选，保留原运行身份与开始时间，不重复已结算批次，并把“已调度但未结算”的整个批次作为原子提交单位重新执行。没有检查点的历史未完成运行返回 `candidate_state_missing`，不得根据不完整身份猜测恢复，也不得静默从头运行。

## 备选方案

- 让 Controller 直接从原始 Session 事件恢复。未采用，因为事件顺序和一致性规则会泄漏给每个调用方。
- 保存并反序列化整个内存工作流对象。未采用，因为其中包含实现细节，会形成脆弱的存储格式。
- 每次中断后从头开始。未采用，因为这会重复已经完成的网络与模型工作，并可能改变稳定查询身份。

## 影响

Session 回放和继续执行现在共享一套带版本的词汇。非法状态不能同时携带继续执行输入与恢复失败。继续执行前会校验检查点身份、已批准计划兼容性、已提交批次数、待处理批次身份及候选载荷完整性。

只有采用检查点契约创建的新运行可以恢复。进程在首个持久批次检查点前崩溃，或历史运行只有调度事件而缺少可执行候选状态时，必须开始新研究。恢复期间有意禁用新的证据缺口检索轮次，因为检查点没有持久化来源运行时的解析缓存；它仍可继续已保留的排序候选池，需要新检索轮次时会明确记录限制。
