# Agent Note: Academic 运行先执行有界明确查询，再进入一次论文处理流程

Status: implemented

[English](2026-09-18-academic-explicit-query-orchestration.md) | 中文

## 问题

Web Remote 原先只接收一个搜索字符串，工作流也只调用一次多来源搜索接口。研究简报包含多个独立问题时，拼成一条查询可能产生无法同时满足的条件。例如，2017 年的 Transformer 论文不可能同时提到后来才提出的 BERT。来源普遍失败时，一条不透明的长查询也难以定位问题。

## 决策

现有浏览器请求保留 `query: string` 字段。Controller 将非空行解释为有序明确查询，去除首尾空白和完全重复项，最多接受三条。查询数还必须符合已批准 Research Brief 的 `maximumSearchRounds`；数量非法时，在占用维护阶段前拒绝。现有单行调用保持不变。

`DraftPipelineInput` 改为携带有序 `searches`。工作流按顺序通过 B 不变的单查询 `searchAll()` 适配器执行。某个已完成批次含有来源失败时，不阻止后续明确查询；配置错误或无法表示为批次结果的适配器错误仍向上抛出，取消则不再开始下一条查询。`RetrievalRun.queries` 记录每条已经开始调用适配器的查询，包括调用期间被取消的查询。

已完成的查询批次先按轮转顺序交错，再进入摄取。摄取沿用既有精确标识符归并，随后把一个全局候选成果上限应用于去重结果。这样前一条查询不能占满全部候选名额，同一篇论文被多条查询发现时也不会占多个名额。Provider、发现记录数、限制、截断和失败在已完成批次之间累积。

当前不使用模型规划、改写或追加查询，也不自动重试。

## 考虑过的替代方案

**继续使用一条长查询。** 未采用，因为独立子问题可能需要不同年份和术语的论文，而目录匹配器可能要求所有词同时出现。

**增加大模型查询规划器。** 延后，因为这会在明确查询路径稳定前增加模型成本、不确定性、额外决策记录和新的审批语义。

**并发执行查询。** 本增量未采用，因为顺序执行可以让取消、来源负载、失败归属和 `RetrievalRun.queries` 保持确定。

**去重前应用候选上限。** 未采用，因为不同查询返回的重复记录会占用全局成果预算。

## 结果

Remote 合同对现有 Web 调用保持源码兼容。客户端后续可以改成多行输入，无需修改请求类型。使用两至三条查询的 Brief 计划必须批准相应的 `maximumSearchRounds`。B 保持既有 Provider 接口，C 保持既有结果投影。

工作流和 Controller 聚焦测试覆盖按序执行、候选轮转、跨查询精确去重、来源失败批次后继续、取消、查询规范化及系统或审批上限。自适应查询生成、重试、持久化、进度流和跨运行索引复用继续延期。
