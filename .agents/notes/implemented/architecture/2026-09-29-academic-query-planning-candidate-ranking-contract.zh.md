# Agent Note：学术查询规划与候选排序契约

状态：已实施

[English](2026-09-29-academic-query-planning-candidate-ranking-contract.md) | 中文

## 问题

查询生成、候选排序、工作流调度和 Web 解释需要一套不依赖提供方的交接契约。若没有共享标识与结果结构，检索包和产品包会分别定义不兼容的查询、优先级、覆盖与停止语义。

## 决策

Academic Model 负责 Q1 契约，但不实现查询或排序。`HybridSearchPlan` 把不依赖提供方的学术源、Web 发现和指定站点查询绑定到一个准确的已批准 ResearchBrief 版本。每条计划查询都有 `SearchQueryId`；经过核验的引文扩展则指明作为种子的成果版本。查询和覆盖记录保存 Brief 中的原始问题字符串，因为 ResearchBrief 当前没有问题 ID，Q1 也不改写已经批准的 Brief 历史。

`InclusionTargets` 分开表示最低交付数量、期望目标和绝对上限。`ACADEMIC_CANDIDATE_RANKING_POLICY_V1` 集中保存已批准的百分制权重及 P0/P1/P2 阈值。排序器直接使用 Q3 的成果、规范版本和查询来源，不再把这些记录复制到另一份输入中。共享 `CandidateAssessment` 补充可信提供方摘要与关键词可用状态、语义比例、已审核规则判定和 Controller 生成的全文解析事实。Web 发现摘要绝不提供学术正文；未解析和未知的全文状态均不等于已经确认可解析。

候选结果以稳定代码和可选审核细节公开硬过滤原因，同时公开分类、全部加权分项、最终优先级、匹配问题、多样性标签和非空决定理由。`AcademicCandidateRankingResult` 将这些评估绑定到准确 Brief 版本，并通过有权威顺序的 P0/P1/P2/excluded ID 队列准确返回每个成果版本一次。无论分数多少，硬过滤排除都必须得到 excluded 优先级。共享辅助函数校验目标顺序、查询来源、评分范围与总分、优先级、已审核问题和队列成员关系，但不负责分类或给论文打分。

问题覆盖为 Brief 中每个原始问题列出支撑成果、证据和剩余缺口。检索轮次与停止决定区分继续执行和终止原因。进度事件草案携带单调序号、当前阶段、轮次／查询／批次／成果身份、实际候选漏斗计数、问题覆盖计数和可选终止原因，不保存估算百分比。

Q1 不修改现有运行时工作流。B 负责生成查询和评估候选，A 在后续工作包负责批次调度与停止判断，C 负责解释和进度界面。三者共同使用一份合成固定样例作为可执行交接。

## 影响

B 和 C 使用同一套评估与排序结果类型，不再重新包装 Q3 记录。A 准备已审核判断，后续通过队列 ID 消费顺序，不导入 B 的实现。评分或阈值变化必须通过明确策略表达，不能散落为常量。若未来增加稳定问题 ID，需要单独审核 ResearchBrief 结构变更。运行时 Session 事件、持久化、模型辅助语义分类和补检仍属于后续工作。

## 验证

Academic Model 与 Academic Retrieval 聚焦测试验证查询身份、纳入目标顺序、评分计算与准确优先级边界、错误策略、准确问题引用、完整且唯一的队列成员关系、硬过滤代码和确定性队列顺序。包级类型检查和静态检查覆盖所有公共导出。

## 考虑过的替代方案

**在检索包和 Web 包各自声明类型。** 这会让 B 与 C 重复定义语义，并迫使 A 在互相竞争的结构之间转换。

**在 Q1 给 ResearchBrief 增加问题 ID。** 稳定问题身份以后可能有用，但修改已批准 Brief 记录超出了本次共享交接范围。

**把排序算法放进 Academic Model。** 模型只应校验公开值与策略不变量；确定性分类和排序仍由 B 负责。以后如增加模型辅助分类器，需要单独审核适配器和持久模型调用记录。

**让 B 直接读取 Controller 服务。** 这会让纯排序器耦合提供方拓扑，也使 A 的调度器无法重放相同候选事实。Controller 应先解析全文可用性，再调用排序器。
