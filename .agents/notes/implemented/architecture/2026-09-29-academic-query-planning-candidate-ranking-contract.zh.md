# Agent Note：学术查询规划与候选排序契约

状态：已实施

[English](2026-09-29-academic-query-planning-candidate-ranking-contract.md) | 中文

## 问题

查询生成、候选排序、工作流调度和 Web 解释需要一套不依赖提供方的交接契约。若没有共享标识与结果结构，检索包和产品包会分别定义不兼容的查询、优先级、覆盖与停止语义。

## 决策

Academic Model 负责 Q1 契约，但不实现查询或排序。`HybridSearchPlan` 把不依赖提供方的学术源、Web 发现和指定站点查询绑定到一个准确的已批准 ResearchBrief 版本。每条计划查询都有 `SearchQueryId`；经过核验的引文扩展则指明作为种子的成果版本。查询和覆盖记录保存 Brief 中的原始问题字符串，因为 ResearchBrief 当前没有问题 ID，Q1 也不改写已经批准的 Brief 历史。

`InclusionTargets` 分开表示最低交付数量、期望目标和绝对上限。`ACADEMIC_CANDIDATE_RANKING_POLICY_V1` 集中保存已批准的百分制权重及 P0/P1/P2 阈值。候选结果公开硬过滤决定、分类、全部加权分项、最终优先级、匹配问题、多样性标签和非空决定理由。无论分数多少，硬过滤排除都必须得到 excluded 优先级。共享辅助函数校验目标顺序、评分范围、权重总和及阈值顺序，但不负责分类或给论文打分。

问题覆盖为 Brief 中每个原始问题列出支撑成果、证据和剩余缺口。检索轮次与停止决定区分继续执行和终止原因。进度事件草案携带单调序号、当前阶段、轮次／查询／批次／成果身份、实际候选漏斗计数、问题覆盖计数和可选终止原因，不保存估算百分比。

Q1 不修改现有运行时工作流。B 负责生成查询和评估候选，A 在后续工作包负责批次调度与停止判断，C 负责解释和进度界面。三者共同使用一份合成固定样例作为可执行交接。

## 影响

B 和 C 可以直接开始 Q2/Q3 与 Q6，无需声明替代类型。评分或阈值变化必须通过明确策略表达，不能散落为常量。若未来增加稳定问题 ID，需要单独审核 ResearchBrief 结构变更。运行时 Session 事件、持久化、查询生成、语义分类、排序算法和补检仍属于后续工作。

## 验证

Academic Model 聚焦测试验证查询 ID 创建、纳入目标顺序、评分计算与准确优先级边界、错误策略，以及 Q1 固定样例的全部跨记录引用。包级类型检查和静态检查覆盖所有公共导出。

## 考虑过的替代方案

**在检索包和 Web 包各自声明类型。** 这会让 B 与 C 重复定义语义，并迫使 A 在互相竞争的结构之间转换。

**在 Q1 给 ResearchBrief 增加问题 ID。** 稳定问题身份以后可能有用，但修改已批准 Brief 记录超出了本次共享交接范围。

**把排序算法放进 Academic Model。** 模型只应校验公开值与策略不变量；检索智能和模型辅助分类仍由 B 负责。
